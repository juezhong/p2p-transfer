# P2P Transfer v0.1.0-test.8 — 双向任务取消、绝对路径进度与终端退出修复

开发阶段 **Pre-release**，不是稳定生产版。为 Linux x86_64 ↔ RK3568 ARM64 真实 LAN 双机 test.7 反馈准备。本版遵循用户明确要求继续保持 Go v0.16.4 风格的启动目录和全文件系统访问（使用当前进程的文件权限）。

## 修复清单

- **任意一端可取消当前文件传输**：Control RPC 的取消目标来自会话内实际登记的发送或接收任务，而不是仅来自本机 PUT/GET 命令；`cancel` 与 Ctrl-C 均可作用于远端发起的正在进行的传输。局部取消不会主动关闭 Control 或四条 Data QUIC。
- **等待取消不阻塞 Control**：发送对端的 CancelTransfer RPC 在独立 Tokio 任务中等待真正停止后的确认，本机继续受理对端的 Control 请求。避免双方同时取消时在同一个事件循环内互相等待的死锁。
- **进度改为只显示预计剩余时间**：继续显示 SHA/写盘 ACK 驱动的百分比、字节和速率，不再显示已经传输了多久；发送和接收显示的文件路径均拼接各自设备的真实文件系统根，呈现**本机绝对路径**，不再是 `root/p2p-transfer/...` 等缺少前导 `/` 的中间内部路径。
- **终端清理和退出提示**：help 与欢迎文案明确列出 `quit / exit`。输入线程收到退出命令后直接结束，不会在程序关闭阶段又启动新的提示符；Unix 原始终端设置在退出路径恢复，并清理终端应用绘制的状态行和输入行，避免污染上层 Shell 提示符。
- **任务状态归属**：状态展示同时包含来自任意一方的活动发送/接收，不误把远端发起的文件传输标成空闲。较早请求的取消回调不得清空后来开始的文件进度。

## 自动验证 / 真实双机复测

发布流水线须先通过 Rust Checks、五平台 Debug、七目标 Preview（包括真实双进程本机回归及取消在途 QUIC 测试），合并 main 后重新构建七个发布附件并附 SHA256SUMS.txt，全部成功才生成这个 Release。

实机优先测试：① A `put 2GB.bin`、B 输入 `cancel` 或 Ctrl-C；② B `get 2GB.bin`、A 输入 `cancel` 或 Ctrl-C；③ 双方几乎同时取消；④ 取消后双方 status 的租约和进度清零，Control/Data 仍能工作，再次 GET/PUT 完成 SHA-256；⑤ 两端输入 `exit` 后系统终端回显/回车/提示符正常。完整 2 GiB 文件成功和非 LAN NAT 的吞吐仍须实测。

**安全提示：** Unix 配对对端可按本机运行账户权限访问整个文件系统；避免以 root 与不可信设备连接。INVITE/REPLY 必须通过可信私密渠道传递。仍无 TURN/Relay，尚未完成断线未确认分块重传及四 Data 并行 striping。

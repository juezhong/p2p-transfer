# p2p-transfer v0.1.3 — 通用 Link SDK 迁移与双摘要命令

**发布基线：** v0.1.2，且严格按 SDK-first 顺序迁移：先合并 [p2p-sdk #73](https://github.com/juezhong/p2p-sdk/pull/73)（SDK `7b7873c46c9f66f8eedef28b7cd7e53c97ba32e4`），再升级 Transfer 锁定的 SDK Git commit。

## 更新

- **SDK 与业务职责分离：** SDK 对外只创建/管理通用、已认证的 QUIC Link（bootstrap 与可请求的额外 Link）；SDK 不定义业务 Control/Data，不固定 4 条连接，不调度文件流。
- Transfer 自行决定初始 Link 的 Control RPC 用途，并在成功配对后向 SDK 申请 4 条额外 Link 作为 Transfer Data lane；SDK 独立维持物理连接、mTLS/PIN/HMAC 认证与状态，Transfer 决定应用业务含义和任务生命周期。
- **本机 `checksum <文件>`：** 以一次 128 KiB 分块的流式读操作计算 SHA-256、MD5，输出类似系统校验命令的两行摘要及本机绝对路径。支持中文/空格/绝对与本地相对路径和 Tab 补全；旧 `sha256` 与 `md5` 命令保留。
- 继续不显示 GET 发送端的「已回传 N 字节」重复提示，接收端保持 SHA-256 落盘验证。

## 平台与校验

流水线需验证 Rust fmt、Clippy、工作区测试、7 个发行目标编译和校验；提供 Linux x86_64/aarch64 的 GNU 和 musl、macOS x86_64/aarch64、Windows x86_64 二进制与 SHA256SUMS.txt。

## 兼容性与限制

- SDK 内部采用与旧版相同的 Bootstrap/Additional HMAC 标签字节值和 mTLS/PIN 校验机制；**新旧版本实际互通需要另外实测，暂不承诺兼容混用**，建议双方同时升级。
- SDK 的 Link 重拨只修复物理传输，不恢复已经断开的 QUIC Stream、应用文件 ACK/块或整个传输任务；文件级续传和复杂 NAT/CGNAT/IPv6 现场可靠性仍未完成。
- SDK 首条 bootstrap Link 关闭后，额外 Link 的实际跨 NAT 可达性以及端口映射延续仍需要实体设备长时测试。
- `MD5` 不抗碰撞，仅用于非对抗性的快速文件比对；身份验证和传输完整性继续依赖 TLS/会话认证与 SHA-256。
- Unix 默认配对方可按运行账户权限访问全部文件系统；请勿以 root 与不可信设备配对或泄露 INVITE/REPLY。

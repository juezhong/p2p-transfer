# p2p-transfer v0.1.4 — CLI 校验队列与终端稳定性维护

**来源**：以 `v0.1.3` 的传输协议和 SDK 稳定基线为基础，纳入已合并的 [Transfer PR #46](https://github.com/juezhong/p2p-transfer/pull/46) 的 CLI 层修复。与 [v0.1.3](https://github.com/juezhong/p2p-transfer/releases/tag/v0.1.3) 相比，本次版本只升级 CLI 版本元数据及发行说明，**不修改 SDK、`transfer-core`、配对认证与文件传输协议**。

## 改进

- **单个校验任务**：`checksum <本机文件>`、`sha256 <本机文件>`、`md5 <本机文件>` 接受后阻塞本机新命令的提示符，传输进行中先等待双方传输完成，再打开目标文件计算。既不启动多个重复校验，也不阻塞后台 Control/Data 收发与网络状态更新。
- **清晰的状态反馈**：立即显示校验已接受，等待传输、开始计算和最终完成都有可见提示。固定缓冲流式读取文件，`checksum` 单次读取同时计算 SHA-256 和 MD5，仍支持本地绝对/相对路径。
- **终端体验**：稳定单行进度条（百分比、已传/总量、MiB/s、剩余时间、文件路径）；暂停命令输入时仍原位刷新进度，保留中文输入、Tab 补全、Ctrl-C 和终端状态恢复行为。
- **失败说明**：接收端文件写入或完整性校验失败后明确报告本次传输**尚未成功**，不把另一端 `RemoteRejected` 当作已完成传输。

## 平台与校验

正式流水线执行 Rust 格式检查、Clippy、工作区测试、七平台测试/优化构建，并生成以下七个可执行文件及 `SHA256SUMS.txt`：Linux x86_64/aarch64（GNU 与静态 musl）、macOS x86_64/aarch64、Windows x86_64。建议两端都更新到 v0.1.4，以保持提示与任务处理行为一致。

## 已知限制

- 旧日志中的 `Transfer(Filesystem(Io))` 是接收侧文件操作错误，`Transfer(RemoteRejected)` 是对端拒绝确认。**没有原始 OS errno 的情况下不能确诊根因；错峰校验只是减少额外磁盘 I/O 竞争，不构成对该错误已彻底修复的证明。**
- Linux x86_64 ↔ RK3568 的 2GiB GET、源文件传输期间触发 checksum、最终 SHA-256 对比与存储故障注入还需实体设备验收。不要把 GitHub Actions 构建成功当作现场 I/O 问题已验证解决。
- 未完成数据块断线自动重传、四路数据流 striping、TURN/Relay 与跨 NAT/CGNAT 长时间现场验收，限制与 v0.1.3 相同。
- Unix 端配对对端可按进程权限访问当前文件系统；不得使用 root 与不可信设备配对，务必保密 INVITE/REPLY。
